# Security

Every submission is untrusted text that ends up as an argument to a C program
that parses files. The controls below are the ones that follow from that.

## External process execution

All process starts go through `app/search/subprocess_utils.run_tool`. There is
no other `subprocess` call in the codebase.

```python
subprocess.Popen(
    [resolved_binary, *args],   # argument list
    shell=False,                # no shell, ever
    stdin=subprocess.DEVNULL,
    stdout=out_fh, stderr=err_fh,   # files, not pipes
    env=minimal_env,
    start_new_session=True,     # own process group
)
```

* **Command injection** — `shell=False` with a list. No user-controlled text
  is ever concatenated into a command string, and in fact no user-controlled
  text reaches the command line at all: FASTA headers are replaced with `Q1`,
  `Q2`, … before the query file is written, and every path argument is
  generated by the server.
* **Process hangs** — every call has a mandatory timeout. On expiry the whole
  process group is killed (`SIGTERM`, then `SIGKILL`), so grandchildren of
  MAFFT and MMseqs2 do not survive the request.
* **Memory exhaustion in the parent** — stdout and stderr go to files. A tool
  that emits gigabytes fills a disk quota rather than the web process's heap;
  only the last 4 kB of stderr is read into memory for the log.
* **Credential leakage into children** — the child environment is rebuilt from
  scratch with `PATH`, `HOME`, `TMPDIR` and `LC_ALL`. Database credentials are
  not in it.

## Input validation

Enforced in `app/fasta.py` and the route layer, in this order:

| control | setting | default |
|---|---|---|
| request body size (rejected before reading) | `ENZYMEX_MAX_UPLOAD_BYTES` | 1 MB |
| upload read cap (independent of `Content-Length`) | same | 1 MB |
| sequence count | `ENZYMEX_MAX_QUERY_SEQUENCES` | 10 |
| residues per sequence | `ENZYMEX_MAX_QUERY_LENGTH` | 5,000 |
| concurrent searches | `ENZYMEX_MAX_CONCURRENT_JOBS` | 2 |

Structural validation rejects, with a message the submitter can act on:
missing FASTA header, header with no residues, duplicate identifiers,
duplicate sequences, characters outside the IUPAC protein alphabet, internal
stop codons, and nucleotide sequences (detected compositionally, since
A/C/G/T/U/N are also valid amino acid letters).

Headers are sanitised for storage — control characters removed, tabs to
spaces, truncated to 120 characters — and then carried only as display text.
Escaping is the template engine's job.

## Path handling

Job identifiers are 16 hex characters from `secrets.token_hex`, generated
server-side. Nothing user-supplied becomes part of a path.

`app/jobs.job_dir` validates against `^[0-9a-f]{16}$` *and* re-checks that the
resolved path's parent is the job root, so `../`, absolute paths and encoded
variants all fail before any filesystem call. Directories are created with
`exist_ok=False` (a collision is an error, never a silent reuse) and mode
`0700`.

## Output handling

Jinja2 autoescaping is on and set explicitly rather than relied on by default,
because the results page renders user-supplied FASTA headers and
database-supplied descriptions. `tests/test_web.py` asserts that a
`<script>` header comes back escaped and that no filesystem path appears in a
rendered page.

User-facing error messages are written by hand and never include a path, a
command line, a stack frame or a tool's stderr. Those go to the server log.
The generic 500 handler logs the traceback and returns a fixed message.

## Database

See `docs/database.md`. In summary: `SELECT`-only grant, `SET SESSION
TRANSACTION READ ONLY` on every connection, an explicit
`ENZYMEX_DB_CONFIRM_COPY=true` acknowledgement before any connection is
opened, `SecretStr` for the password, identifier validation against
`[A-Za-z0-9_$]` before interpolation, bound parameters for all values, and no
database access at all from the request path.

## Secrets

`.env` is gitignored. `.env.example` carries keys with empty values. The
password is a `SecretStr`, so it renders as `**********` in `repr`, in logs
and in exception text. `/health` reports `user@host:port/database` only.
`git check-ignore .env` is worth running once after cloning.

## Cross-job isolation

Each job gets its own directory; the query file, every raw tool output and the
normalized result live inside it. Nothing is written to a shared scratch path,
so two concurrent submissions cannot collide on a filename or read each
other's intermediates. `tests/test_e2e.py::test_job_directories_do_not_contaminate_each_other`
covers this.

Job directories are swept on each new submission using
`ENZYMEX_JOB_RETENTION_HOURS`. Setting `ENZYMEX_KEEP_RAW_OUTPUTS=false` drops
the tool output immediately and keeps only the normalized result.

## What is deliberately not here

* **Authentication.** There is none. This is an internal test server; put a
  reverse proxy with auth in front of it if it is reachable beyond the box.
* **Rate limiting per client.** The concurrency semaphore bounds total work,
  but there is no per-IP limit. Add one at the proxy if needed.
* **CSRF protection.** The only state-changing endpoint creates a
  throwaway job from data the submitter supplies; there is nothing to forge.
  This changes the moment authentication is added.
